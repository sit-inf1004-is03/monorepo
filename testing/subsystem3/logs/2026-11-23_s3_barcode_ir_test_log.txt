3. Bench bring-up: faults found and cleared (Wing, before 20 Nov)
----------------------------------------------------------------
3a. Barcode sensor read on the wrong pin (serial monitor, COM3)

Old main_example build, barcode sensor on the breadboard, sensor moved
by hand over black and white throughout the capture.

---- begin capture: 10 lines, verbatim ----
pin = 1
pin = 1
pin = 1
pin = 1
pin = 1
pin = 1
pin = 1
pin = 1
pin = 1
---- Closed the serial port COM3 ----
---- end capture ----

Analysis: the reading never changes anywhere in the capture, with the
sensor physically moved over black and white and its indicator LED
seen to switch.  The header had BARCODE_PIN = 2U while every other
source (app.h, the team pin map) said GP4, so GP2 was being read and
GP4 was never watched.  GP2 floats high through its pull-up, which is
the constant 1.
Fix: BARCODE_PIN = 4U.
Result: FIXED.
3b. Analog output not connected (AO vs DO bench, Maker Pi Pico)

Bench comparison of the sensor's analog output (AO, read on the ADC)
against its digital output (DO, the on-board comparator).  SW is the
software black/white decision taken from AO.

---- begin capture: 9 lines, verbatim ----
AO=  32 |................................| SW=  ?   DO=BLACK
AO=  32 |................................| SW=  ?   DO=BLACK
---- contrast so far: min=25 max=34 span=9 ----
AO=  30 |................................| SW=  ?   DO=BLACK
AO=  31 |................................| SW=  ?   DO=BLACK
AO=  32 |................................| SW=  ?   DO=BLACK
AO=  33 |................................| SW=  ?   DO=BLACK
AO=  32 |................................| SW=  ?   DO=BLACK
AO=  33 |................................| SW=  ?   DO=BLACK
---- end capture ----

Analysis: AO sits at 30-34 of 4095 for the whole capture and the
running contrast line reports span=9, over both black and white.  The
AO lead was not plugged in, so the ADC pin was floating.  SW = '?' is
correct behaviour, not a bug: the software refuses to call black or
white below its minimum contrast.  DO still reads BLACK because the
comparator output is a separate wire that was connected.
Fix: wire AO to the ADC pin.
Result: FIXED.
3c. ADC device would not open (line task, both channels)

Line task running, both line sensors wired, WHITE/BLACK constants
still at their placeholder values.  dd is the device descriptor from
tk_opn_dev(); er is the return of tk_srea_dev().

---- begin capture: 6 lines, verbatim ----
dd=-42 er=-18 C=   0 R=   0 lvl=7 on
dd=-42 er=-18 C=   0 R=   0 lvl=7 on
dd=-42 er=-18 C=   0 R=   0 lvl=7 on
dd=-42 er=-18 C=   0 R=   0 lvl=7 on
dd=-42 er=-18 C=   0 R=   0 lvl=7 on
dd=-42 er=-18 C=   0 R=   0 lvl=7 on
---- end capture ----

Analysis: the decisive capture of the whole bring-up.  Both sensors
read 0 and no wiring change made any difference.  Printing the device
descriptor and the read error showed dd = -42 (E_NOEXS, object does
not exist) and er = -18 (E_IO): tk_opn_dev() was failing, so every
read returned the error value 0.  The RP2040 driver registers A/D
unit 0 as "adca" (DEVCNF_ADC_DEVNAME plus the unit letter), not
"adc".
Fix: tk_opn_dev("adca").
Note for the report: the fault was invisible until the descriptor and
the error code were printed.  The symptom on its own (two channels
reading zero) pointed at wiring, which was not the cause.
Result: FIXED.
